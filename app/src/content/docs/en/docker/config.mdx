In today's containerized world, securing your Docker daemon API is paramount, especially when orchestrating services like reverse proxies (e.g., Traefik) on the same host. While Docker offers incredible flexibility, its default configurations can expose your environment to unnecessary risks. This article delves into a robust security architecture that marries Docker's native features with network hardening techniques to create an ironclad defense around your container ecosystem.

This advanced security blueprint integrates:

- **User Namespace Remapping (`userns-remap`)**: A fundamental isolation mechanism that strips containers of true root privileges on the host.
- **Dummy Network Interface**: Crafting a dedicated, internal-only network segment for your Docker API, far from external reach.
- **Mutual TLS (mTLS)**: Implementing a powerful two-way authentication and encryption layer for all API communications.
- **Uncomplicated Firewall (UFW)**: Strategically defining network rules to permit only authorized, internal traffic to the API endpoint.

## The Imperative for Enhanced Docker API Security

Conventionally, exposing the Docker API over a standard TCP port without robust authentication is a significant vulnerability. Even when utilizing `userns-remap` for rootless container execution, the API endpoint itself can remain an attack vector for other processes or compromised containers on the same machine.

Furthermore, the common practice of directly mounting `/var/run/docker.sock` into containers, while convenient for tools like Traefik, carries inherent risks. A breach in such a container could grant an attacker full control over your Docker daemon, enabling them to spawn malicious containers or disrupt your entire infrastructure.

Our proposed solution meticulously addresses these concerns by:

- **Eliminating Direct Socket Mounting**: Transitioning clients like Traefik to communicate with a TCP endpoint instead of direct socket access.
- **Creating an Isolated API Gateway**: Binding the Docker API to a virtual dummy interface, ensuring it's never directly exposed to external networks.
- **Enforcing Strict Authentication**: Employing mTLS to mandate cryptographic verification for both the client (e.g., Traefik) and the Docker daemon, ensuring only trusted entities can interact.
- **Building a Multi-Layered Defense**: Combining user remapping, network segmentation, strong encryption, and firewalling to create a resilient security posture.

## Phase 1: Establishing the Docker Foundation

This initial phase focuses on [installing the Docker Engine](https://docs.docker.com/engine/install/ubuntu/) and configuring basic security via user namespace remapping on your Ubuntu system.

### Step 1.1: Pruning Legacy Docker Packages

Begin by meticulously removing any previous or conflicting Docker-related installations to ensure a clean slate.

```bash
for pkg in docker.io docker-doc docker-compose docker-compose-v2 podman-docker containerd runc; do sudo apt-get remove $pkg; done
```

_Rationale_: This preemptive cleanup prevents potential conflicts and ensures a smooth installation of the official Docker Engine.

### Step 1.2: Installing Docker Engine

#### Step 1.2.1: Integrating Docker's Official APT Repository

Set up the official Docker APT repository to guarantee access to the latest, stable Docker releases.

```bash
# Fetch Docker's GPG key:
sudo apt-get update
sudo apt-get install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Incorporate the Docker repository into your Apt sources:
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
```

_Rationale_: This sequence of commands ensures your system can securely download and verify Docker packages directly from the official source.

#### Step 1.2.2: Deploying Docker Core Components

Install the essential Docker components that comprise the engine.

```bash
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

_Rationale_: This command installs the Docker Community Edition daemon, its command-line interface, the `containerd` runtime, and vital plugins for building and orchestrating containers.

### Step 1.3: Verifying Docker's Operational Status

Confirm that your Docker installation is fully functional.

```bash
sudo docker run hello-world
```

_Rationale_: Executing the `hello-world` image is a quick and effective way to confirm that the Docker daemon is running and responsive.

## Phase 2: Fortifying Docker with User Namespace Remapping & mTLS

This phase implements [`userns-remap`](https://docs.docker.com/engine/security/userns-remap/) for enhanced host isolation and sets up mutual TLS (mTLS) for secure API communication.

### Step 2.1: Activating User Namespace Remapping (`userns-remap`)

Configure Docker to remap container root privileges to a non-privileged user on the host system, significantly reducing the attack surface.

> **Why `userns-remap` is crucial**: By preventing a container's root user from having root privileges on the host, you mitigate the risk of privilege escalation if a container is compromised. This remapping assigns a range of unprivileged User IDs (UIDs) and Group IDs (GIDs) to the container's root, effective only within its isolated namespace.

#### Step 2.1.1: Reviewing Existing UID/GID Mappings (Optional)

You can inspect current `subuid` and `subgid` mappings on your system.

```bash
grep -E '^(root|dockremap)' /etc/subuid /etc/subgid
cat /etc/subuid
```

_Rationale_: These files define the ranges of UIDs and GIDs available for user namespaces. Post-configuration, Docker will typically add entries for an internal `dockremap` user.

#### Step 2.1.2: Modifying `/etc/docker/daemon.json`

Create or update your Docker daemon's configuration file.

```bash
sudo nano /etc/docker/daemon.json
```

Insert the following configuration:

```json
{
  "userns-remap": "default",
  "experimental": false,
  "storage-driver": "overlay2"
}
```

_Rationale_:

- `"userns-remap": "default"`: Enables automatic creation of the `dockremap` user and its UID/GID mapping ranges.
- `"experimental": false`: Disables potentially unstable experimental features.
- `"storage-driver": "overlay2"`: Specifies the recommended and high-performance [`overlay2`](https://docs.docker.com/engine/storage/drivers/overlayfs-driver/) storage driver for Linux systems.

#### Step 2.1.3: Restarting Docker to Apply Changes

A daemon restart is essential for `userns-remap` to take effect. Be aware that this will invalidate existing images and containers, requiring them to be rebuilt or re-pulled.

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

_Rationale_: `daemon-reload` refreshes systemd's configuration, and `restart docker` applies the new `daemon.json` settings.

#### Step 2.1.4: Confirming `userns-remap` Activation

Verify that the `dockremap` user has been successfully created by Docker.

```bash
getent passwd dockremap
```

_Example Output_: `dockremap:x:997:985::/home/dockremap:/bin/sh`

```bash
id dockremap
```

_Example Output_: `uid=997(dockremap) gid=985(dockremap) grupos=985(dockremap)`
_Rationale_: These commands confirm the existence and details of the `dockremap` user, which Docker uses for user remapping.

### Step 2.2: Implementing Mutual TLS for Docker API

Set up cryptographic authentication for your Docker API using custom scripts and OpenSSL configuration files from the provided GitHub repository.

#### Step 2.2.1: Preparing the Certificate Management Environment

Clone the necessary repository containing the scripts and OpenSSL templates to `/opt/docker_conf_m8`.

```bash
# IMPORTANT: Set your desired Docker API dummy interface IP (e.g., 10.254.254.1)
export DOCKER_HOST_IP="YOUR_DOCKER_HOST_IP_HERE" # <<< REPLACE THIS PLACEHOLDER!
BASE_DIR="/opt/docker_conf_m8"

# Clone the project repository
sudo git clone https://github.com/mano8/docker_conf_m8.git "${BASE_DIR}"
sudo chmod 700 "${BASE_DIR}" # Secure the base directory
```

_Rationale_: This step downloads all essential files for certificate generation. **Ensure you replace `"YOUR_DOCKER_HOST_IP_HERE"` with the static IP you intend for your Docker API dummy interface.** This IP will be embedded in your server and client certificates for secure validation.

The `docker_conf_m8` repository ([https://github.com/mano8/docker_conf_m8](https://github.com/mano8/docker_conf_m8)) contains:

- **`scripts/validate_docker_host_ip.sh`**: Validates the `DOCKER_HOST_IP` environment variable.
  - [Link to script](https://github.com/mano8/docker_conf_m8/blob/main/scripts/validate_docker_host_ip.sh)
- **`ssl_conf/ssl_docker_server.conf`**: OpenSSL template for the Docker daemon's server certificate, dynamically adjusted with your `DOCKER_HOST_IP`.
  - [Link to config](https://github.com/mano8/docker_conf_m8/blob/main/ssl_conf/ssl_docker_server.conf)
- **`ssl_conf/ssl_docker_client.conf`**: OpenSSL template for the client certificate (e.g., for Traefik), also dynamically adjusted.
  - [Link to config](https://github.com/mano8/docker_conf_m8/blob/main/ssl_conf/ssl_docker_client.conf)
- **`scripts/manage_docker_certs.sh`**: The main script for automating CA, server, and client certificate generation, including permission management.
  - [Link to script](https://github.com/mano8/docker_conf_m8/blob/main/scripts/manage_docker_certs.sh)

#### Step 2.2.2: Initiating Certificate Generation

Execute the primary script to generate all necessary mTLS assets.

```bash
sudo "${BASE_DIR}/scripts/manage_docker_certs.sh" generate
```

_Rationale_: This command orchestrates the creation of:

- **Server Certificates**: `ca.pem`, `server-key.pem`, `server-cert.pem` located in `/etc/docker/certs/` (for the Docker daemon itself).
- **Client Certificates**: `ca.pem`, `client-key.pem`, `client-cert.pem` stored in `/opt/docker_conf_m8/certs/` (for secure client applications like Traefik).
  The client certificate directory will be correctly owned by the `dockremap` user for compatibility with user-namespace remapping.

## 3. Configure the Dummy Interface

To configure the `docker0` dummy interface, it's crucial to determine your system's network management system. Methods vary primarily based on your distribution (Debian, Ubuntu, Linux Mint) and its purpose (server or desktop).

**Very Important:** You must choose **ONLY ONE** method below to configure the `docker0` interface. Using multiple methods for the same interface can lead to conflicts and unpredictable network behavior.

To help you choose, here are the most common scenarios:

* **Netplan:** Standard on **Ubuntu servers** and **modern Ubuntu Desktop installations**. It's an abstraction layer that generates configuration for either `systemd-networkd` (default) or `NetworkManager`.
    * *Quick Check:* Look for a YAML file in `/etc/netplan/` (e.g., `01-netcfg.yaml`).
* **NetworkManager:** Standard on most **desktop systems (Ubuntu Desktop, Linux Mint, Debian Desktop)**, offering dynamic network management and a graphical interface.
    * *Quick Check:* Run `systemctl is-active NetworkManager` (should show `active`) and `nmcli general status`.
* **`ifupdown`:** The traditional system on **Debian Server installations** (and some older Ubuntu versions) where configurations are made directly in `/etc/network/interfaces`.
    * *Quick Check:* Look for specific configurations in `/etc/network/interfaces`.

Once you've identified the most likely network manager for your system, follow the steps in the corresponding section.

### 3.1. Configure Dummy Interface with Netplan (For Systems Using Netplan)

Follow these steps if you've determined your system uses **Netplan**. **If you've previously created direct `systemd-networkd` files (e.g., in `/etc/systemd/network/`) for this interface, please remove them before proceeding to avoid conflicts.**

#### 3.1.1. Create the Netplan Configuration for `docker0`

Create a new Netplan YAML file.

```bash
sudo nano /etc/netplan/99-docker-dummy-interface.yaml
```

Paste the following content. Adjust `10.254.254.1/24` if your `DOCKER_HOST_IP` differs.

```yaml
network:
  version: 2
  renderer: networkd # For servers, 'networkd' is generally the preferred backend. For desktops where NetworkManager manages everything, you might consider 'NetworkManager'.
  netdevs:
    docker0:
      kind: dummy
  ethernets:
    docker0:
      addresses: [10.254.254.1/24]
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8] # Optional: add DNS servers
```

*Explanation*:
* `version: 2`: Specifies the Netplan configuration version.
* `renderer: networkd`: Directs Netplan to use `systemd-networkd` as its backend. Choose `NetworkManager` if it's your primary manager for all interfaces and you want it to also manage this dummy interface.
* `netdevs`: Defines the virtual network device `docker0` as a dummy interface.
* `ethernets`: Configures the `docker0` interface with the static IP address. Ensure this IP matches the `DOCKER_HOST_IP` from your certificates.

#### 3.1.2. Apply Netplan Configuration

First, check the configuration for syntax errors.

```bash
sudo netplan try
```

If `netplan try` reports no errors, apply the configuration permanently.

```bash
sudo netplan apply
```

*Explanation*: `netplan try` validates your configuration and attempts to apply it temporarily. `netplan apply` applies the changes permanently, generating the necessary backend files and restarting the appropriate service.

### 3.2. Configure Dummy Interface with NetworkManager (For Systems Using NetworkManager)

Follow these steps if you've determined your system uses **NetworkManager** (e.g., Linux Mint, Ubuntu Desktop, Debian Desktop).

#### 3.2.1. Create the `docker0` Dummy Interface and NetworkManager Connection

Use `nmcli` to create a new "dummy" type connection named `docker0` and assign it the IP address.

```bash
# Create the dummy interface
sudo nmcli connection add type dummy con-name docker0 ifname docker0

# Configure the IP address for the docker0 connection
sudo nmcli connection modify docker0 ipv4.addresses 10.254.254.1/24 ipv4.method manual

# Optional: Configure DNS servers (if needed for this interface)
sudo nmcli connection modify docker0 ipv4.dns "1.1.1.1 8.8.8.8"

# Bring the connection up
sudo nmcli connection up docker0
```

*Explanation*:
* `nmcli connection add type dummy con-name docker0 ifname docker0`: Creates a new NetworkManager connection of type "dummy" with connection name `docker0` and interface name `docker0`.
* `nmcli connection modify docker0 ipv4.addresses ... ipv4.method manual`: Sets the IPv4 address for the connection and specifies it's manually configured (statically). Ensure `10.254.254.1/24` matches your `DOCKER_HOST_IP`.
* `nmcli connection modify docker0 ipv4.dns ...`: (Optional) Adds DNS servers if the `docker0` interface needs to resolve names.
* `nmcli connection up docker0`: Activates the new connection, which will bring up the `docker0` interface with its IP address. NetworkManager handles the persistence of this configuration.

### 3.3. Configure Dummy Interface with `ifupdown` (For Systems Using `/etc/network/interfaces`)

Follow these steps if your system uses **`ifupdown`** for network management, which is common on traditional Debian server installations where neither Netplan nor NetworkManager are the primary managers.

#### 3.3.1. Create the Dummy Interface Manually

Since `ifupdown` cannot create "dummy" type interfaces directly through its configuration file, you'll need to create it manually and then make it persistent.

```bash
# Create the docker0 dummy interface (this command is temporary until reboot without config)
sudo ip link add docker0 type dummy
sudo ip link set docker0 up
```

*Explanation*:
* `sudo ip link add docker0 type dummy`: Creates a new virtual network interface of type "dummy" named `docker0`.
* `sudo ip link set docker0 up`: Activates the `docker0` interface.

#### 3.3.2. Make the Interface Persistent via `/etc/network/interfaces`

Edit the main network configuration file to ensure the `docker0` interface is created and configured at boot.

```bash
sudo nano /etc/network/interfaces
```

Add the following lines to the end of the file. Ensure the IP `10.254.254.1` matches your `DOCKER_HOST_IP`.

```
# Configuration for the Docker API dummy interface
auto docker0
iface docker0 inet static
  pre-up ip link add docker0 type dummy || true
  address 10.254.254.1
  netmask 255.255.255.0
  post-down ip link del docker0 || true
```

*Explanation*:
* `auto docker0`: Indicates that the `docker0` interface should be brought up automatically at boot.
* `iface docker0 inet static`: Defines `docker0` as an interface with a static IP configuration.
* `pre-up ip link add docker0 type dummy || true`: This command runs before the interface is brought up. It creates the dummy interface if it doesn't already exist. The `|| true` is used to prevent the command from failing if the interface already exists (e.g., if you created it manually earlier).
* `address 10.254.254.1` and `netmask 255.255.255.0`: Assign the IP address and subnet mask to the interface.
* `post-down ip link del docker0 || true`: This command runs when the interface is brought down, deleting the dummy interface.

#### 3.3.3. Apply the Configuration

To apply the new configuration without rebooting the system (which is often necessary with `ifupdown`), you can try bringing the interface down and then up.

```bash
sudo ifdown docker0
sudo ifup docker0
```

*Note*: On some systems or configurations, a full network service restart (`sudo systemctl restart networking` or a server reboot) might be necessary for changes to take full effect.

*Important*: If you're using `ifupdown`, ensure that `NetworkManager` is not actively managing this interface, and that Netplan is not configured to manage it, to avoid conflicts. Managing different interfaces with different tools is possible, but it adds complexity.

### 3.4. Verify `docker0` Status (Applicable to All Methods)

Regardless of the method you used to configure the dummy interface, check if `docker0` is up and has the correct IP.

```bash
ip addr show docker0
```

*Expected Output*: Similar to previous sections, showing `docker0` with `inet 10.254.254.1/24`.

## Phase 4: Binding Docker Daemon to mTLS & Implementing UFW Security

Configure the Docker daemon to utilize the secure dummy interface with mTLS, then layer on UFW rules for network isolation.

### Step 4.1: Updating Docker Daemon Configuration for mTLS

Re-open `/etc/docker/daemon.json` to instruct Docker to listen on the secure TCP endpoint and enforce mTLS.

```bash
sudo nano /etc/docker/daemon.json
```

Adjust the file to include the `hosts` and `tls*` parameters, retaining your `userns-remap` and `storage-driver` settings.

```json
{
  "userns-remap": "default",
  "experimental": false,
  "storage-driver": "overlay2",
  "hosts": ["unix:///var/run/docker.sock", "tcp://10.254.254.1:2376"],
  "tlsverify": true,
  "tlscacert": "/etc/docker/certs/ca.pem",
  "tlscert": "/etc/docker/certs/server-cert.pem",
  "tlskey": "/etc/docker/certs/server-key.pem"
}
```

_Rationale_:

- `"hosts"`: Defines that Docker will listen on both the local Unix socket (for direct CLI access) and the secure TCP port 2376 on the `10.254.254.1` dummy interface.
- `"tlsverify": true`: Enforces mutual TLS, meaning both server and client must present and verify valid certificates.
- `"tlscacert"`, `"tlscert"`, `"tlskey"`: Specify the paths to the Certificate Authority, server certificate, and server key respectively.

### Step 4.2: Restarting Docker Daemon

Restart Docker to load the updated API and TLS settings.

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

_Rationale_: This reloads `systemd` configurations and restarts Docker, applying the new `daemon.json` parameters.

### Step 4.3: Verifying Secure Remote TLS Connection

Test the mTLS connection from your host's Docker CLI using the client certificates.

#### Step 4.3.1: Setting Docker Environment Variables

Configure your shell's environment to point to the client certificates and the secure Docker API endpoint.

```bash
export DOCKER_TLS_VERIFY="1"
export DOCKER_CERT_PATH="/opt/docker_conf_m8/certs"
export DOCKER_HOST="tcp://10.254.254.1:2376"
```

_Rationale_: These variables instruct the Docker CLI to connect via TLS, verify certificates, and locate your client credentials.

#### Step 4.3.2: Executing a Test Command

Attempt a basic Docker command to confirm connectivity.

```bash
docker ps
```

_Expected Outcome_: A list of running containers (possibly empty) without any TLS handshake errors.
_Rationale_: A successful execution confirms secure communication between your Docker CLI and the daemon over the mTLS-secured TCP endpoint.

## Phase 5: Hardening Network Access with UFW

Configure UFW to create a highly restricted environment for your Docker API.

**CRITICAL SECURITY WARNING**: When enabling UFW, it is absolutely essential to allow SSH traffic _before_ activating the firewall, otherwise you risk losing remote access to your server!

### Step 5.1: Enabling SSH Access (Crucial Pre-requisite)

Permit incoming SSH connections to prevent lockout.

```bash
sudo ufw allow ssh comment 'Allow SSH access'
# If your SSH server runs on a non-standard port (e.g., 2222), use:
# sudo ufw allow 2222/tcp comment 'Allow SSH on custom port'
```

_Rationale_: This rule ensures your SSH connection remains active after UFW is enabled.

### Step 5.2: Defining Default Firewall Policies

Set UFW's default behaviors for incoming and outgoing traffic, then enable the firewall.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw enable
```

_Rationale_: `ufw default deny incoming` provides a strong baseline security policy, blocking all unsolicited inbound connections. `ufw default allow outgoing` facilitates normal outbound network operations. You'll be prompted to confirm enabling UFW; type `y` and press Enter.

### Step 5.3: Permitting Docker API Access from Traefik's Network

Since Traefik runs within a Docker bridge network (`traefik_proxy`) and not directly on the host's network stack, its traffic to the `docker0` dummy interface will originate from that bridge network's subnet. You must explicitly allow this traffic.

First, determine the IP subnet of your `traefik_proxy` network:

```bash
docker network inspect traefik_proxy | grep -A 3 'IPAM' | grep 'Subnet'
```

_Example Output_: `            "Subnet": "172.18.0.0/16",`
_Rationale_: This command extracts the subnet CIDR of your Docker network, which is vital for crafting the precise UFW rule.

Now, add the UFW rule using the identified subnet:

```bash
# IMPORTANT: Replace <TRAEFIK_NETWORK_SUBNET> with the actual subnet (e.g., 172.18.0.0/16) obtained from the command above.
sudo ufw allow in on docker0 from <TRAEFIK_NETWORK_SUBNET> to 10.254.254.1 port 2376 proto tcp comment 'Allow Traefik container to access Docker API'
```

_Rationale_: This rule is crucial for enabling secure communication. It precisely allows incoming TCP traffic on the `docker0` dummy interface _only_ from IP addresses within your `traefik_proxy` Docker network's subnet, specifically targeting the Docker API port (2376) on the dummy interface's IP.

### Step 5.4: Validating UFW Rules

Review your active UFW rules to ensure they are correctly applied.

```bash
sudo ufw status verbose
```

_Rationale_: This command provides a detailed list of all active UFW rules and their status.

## Phase 6: Configuring Traefik for Secure Docker Integration

Finally, set up Traefik to seamlessly connect to your now-secure Docker daemon via mTLS on the dummy interface.

### Step 6.1: Creating `docker-compose.yml` for Traefik

Construct your `docker-compose.yml` file for the Traefik service.

```bash
nano docker-compose.yml
```

Paste the following content, adjusting fields like domain names and passwords:

```yaml
version: "3.8"

services:
  traefik:
    image: traefik:v3.4.0 # Utilizes the latest stable Traefik version
    container_name: traefik
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
    networks:
      - traefik_proxy
    ports:
      - "80:80" # Standard HTTP entrypoint
      - "443:443" # Standard HTTPS entrypoint
      # - "8080:8080" # Optional: Traefik Dashboard (consider additional security if exposed)
    volumes:
      - /etc/localtime:/etc/localtime:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro # For Docker provider's event listening (NOT API access)
      - /etc/traefik:/etc/traefik:ro # Mount Traefik's configuration directory
      - /opt/docker_conf_m8/certs:/etc/traefik/certs:ro # Mount generated client certificates into the container
    environment:
      # Docker Host configuration for mTLS connection
      - DOCKER_HOST=tcp://10.254.254.1:2376
      - DOCKER_TLS_VERIFY=1
      - DOCKER_CERT_PATH=/etc/traefik/certs # Path to client certificates INSIDE the container
      # Basic Traefik settings
      - TZ=Europe/Madrid # Customize your timezone
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.api.rule=Host(`traefik.example.com`)" # Adjust to your dashboard domain
      - "traefik.http.routers.api.entrypoints=websecure"
      - "traefik.http.routers.api.service=api@internal"
      - "traefik.http.routers.api.middlewares=auth"
      - "traefik.http.middlewares.auth.basicauth.users=youruser:$$apr1$$YOURHASHEDPASSWORDHERE" # Generate with 'echo $(htpasswd -nb youruser yourpassword)'
      - "traefik.http.routers.api.tls.certresolver=myresolver" # Essential for HTTPS
      # Global HTTP to HTTPS redirection (optional)
      - "traefik.http.middlewares.redirect-https.redirectscheme.scheme=https"
      - "traefik.http.routers.web-http.rule=HostRegexp(`{host:.+}`)"
      - "traefik.http.routers.web-http.entrypoints=web"
      - "traefik.http.routers.web-http.middlewares=redirect-https"

networks:
  traefik_proxy:
    external: true # Assumes this is an existing bridge network
```

_Rationale_:

- **`image: traefik:v3.4.0`**: Specifies the up-to-date Traefik image.
- **`security_opt: - no-new-privileges:true`**: Enforces a secure runtime environment for Traefik.
- **`volumes`**:
  - `/var/run/docker.sock:/var/run/docker.sock:ro`: Mounted _only_ for Traefik's Docker provider to monitor Docker events. API communication will occur via the TCP endpoint.
  - `/opt/docker_conf_m8/certs:/etc/traefik/certs:ro`: Makes your mTLS client certificates accessible within the Traefik container.
- **`environment`**: Crucially, `DOCKER_HOST`, `DOCKER_TLS_VERIFY`, and `DOCKER_CERT_PATH` configure Traefik to connect to the secure Docker API using mTLS.
- **`networks: traefik_proxy`**: Connects Traefik to a dedicated Docker bridge network. Ensure this network exists (e.g., `docker network create traefik_proxy`).

### Step 6.2: Crafting Traefik's Core Configuration (`/etc/traefik/traefik.yml`)

Create a foundational Traefik configuration file.

```bash
sudo nano /etc/traefik/traefik.yml
```

Insert the following configuration, adapting resolver settings as needed:

```yaml
api:
  dashboard: true
  insecure: false # Set to true if dashboard is exposed on 8080 without auth/TLS

entryPoints:
  web:
    address: ":80"
    http:
      redirections:
        entryPoint:
          to: "websecure"
          scheme: "https"
  websecure:
    address: ":443"

providers:
  docker:
    endpoint: "tcp://10.254.254.1:2376" # Direct connection to the secure Docker API
    tls:
      ca: "/etc/traefik/certs/ca.pem"
      cert: "/etc/traefik/certs/client-cert.pem"
      key: "/etc/traefik/certs/client-key.pem"
      insecureSkipVerify: false # Ensures server certificate verification
    exposedByDefault: false # Requires explicit labels for container exposure

certificatesResolvers:
  myresolver:
    acme:
      email: your-email@example.com # Replace with your email for Let's Encrypt
      storage: "/etc/traefik/acme.json" # Ensure this file is persistently mounted
      httpChallenge:
        entryPoint: web
```

_Rationale_:
