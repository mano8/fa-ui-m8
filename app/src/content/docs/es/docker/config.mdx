En el mundo actual de los contenedores, asegurar la API de tu demonio Docker es primordial, especialmente cuando orquestas servicios como proxies inversos (por ejemplo, Traefik) en el mismo host. Aunque Docker ofrece una flexibilidad increíble, sus configuraciones predeterminadas pueden exponer tu entorno a riesgos innecesarios. Este artículo explora una arquitectura de seguridad robusta que combina las características nativas de Docker con técnicas de endurecimiento de red para crear una defensa impenetrable alrededor de tu ecosistema de contenedores.

Este avanzado esquema de seguridad integra:

* **Remapeo de Espacios de Nombres de Usuario (`userns-remap`)**: Un mecanismo fundamental de aislamiento que despoja a los contenedores de los verdaderos privilegios de root en el host.
* **Interfaz de Red Ficticia (Dummy Interface)**: La creación de un segmento de red dedicado e interno para tu API de Docker, manteniéndolo fuera del alcance externo.
* **TLS Mutuo (mTLS)**: La implementación de una poderosa capa de autenticación y cifrado bidireccional para todas las comunicaciones de la API.
* **Cortafuegos Simple (UFW)**: La definición estratégica de reglas de red para permitir solo el tráfico interno y autorizado al punto de acceso de la API.

## La Imperiosa Necesidad de una Seguridad Reforzada de la API de Docker

Tradicionalmente, exponer la API de Docker en un puerto TCP estándar sin una autenticación robusta presenta una vulnerabilidad significativa. Incluso al usar `userns-remap` para la ejecución de contenedores sin root, el propio punto final de la API puede seguir siendo un vector de ataque para otros procesos o contenedores comprometidos en la misma máquina.

Además, la práctica común de montar directamente `/var/run/docker.sock` en los contenedores, aunque conveniente para herramientas como Traefik, conlleva riesgos inherentes. Una falla en un contenedor así podría otorgar a un atacante control total sobre tu demonio Docker, permitiéndole lanzar contenedores maliciosos o interrumpir toda tu infraestructura.

Nuestra solución propuesta aborda meticulosamente estas preocupaciones al:

* **Eliminar los Montajes Directos de Socket**: Cambiando a clientes como Traefik para que se comuniquen a través de un punto final TCP en lugar de un acceso directo al socket.
* **Crear una Puerta de Enlace API Aislada**: Vinculando la API de Docker a una interfaz ficticia virtual, asegurando que nunca esté directamente expuesta a redes externas.
* **Hacer Cumplir una Autenticación Estricta**: Empleando mTLS para exigir una verificación criptográfica tanto para el cliente (por ejemplo, Traefik) como para el demonio Docker, asegurando que solo las entidades de confianza puedan interactuar.
* **Construir una Defensa de Múltiples Capas**: Combinando el remapeo de usuarios, la segmentación de red, el cifrado fuerte y el cortafuegos para crear una postura de seguridad resiliente.

## Fase 1: Estableciendo la Base de Docker

Esta fase inicial se centra en la instalación del motor Docker y la configuración de la seguridad básica mediante el remapeo de espacios de nombres de usuario en tu servidor Ubuntu.

### Paso 1.1: Eliminar Paquetes Obsoletos de Docker

Comienza eliminando meticulosamente cualquier instalación de Docker previa o conflictiva para asegurar una base limpia.

```bash
for pkg in docker.io docker-doc docker-compose docker-compose-v2 podman-docker containerd runc; do sudo apt-get remove $pkg; done
```

*Justificación*: Esta limpieza preventiva evita posibles conflictos y asegura una instalación sin problemas del Motor Docker oficial.

### Paso 1.2: Instalar Docker Engine

#### Paso 1.2.1: Integrar el Repositorio APT Oficial de Docker

Configura el repositorio APT oficial de Docker para garantizar el acceso a las últimas versiones estables de Docker.

```bash
# Añadir la clave GPG oficial de Docker:
sudo apt-get update
sudo apt-get install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Añadir el repositorio a las fuentes de Apt:
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
```

*Justificación*: Esta secuencia de comandos asegura que tu sistema pueda descargar y verificar de forma segura los paquetes de Docker directamente desde la fuente oficial.

#### Paso 1.2.2: Desplegar Componentes Esenciales de Docker

Instala los componentes principales de Docker que conforman el motor.

```bash
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

*Justificación*: Este comando instala el demonio Docker Community Edition, su interfaz de línea de comandos, el runtime `containerd`, y plugins vitales para la construcción y orquestación de contenedores.

### Paso 1.3: Verificar el Estado Operativo de Docker

Confirma que tu instalación de Docker está completamente funcional.

```bash
sudo docker run hello-world
```

*Justificación*: Ejecutar la imagen `hello-world` es una forma rápida y efectiva de confirmar que el demonio Docker está funcionando y responde.

## Fase 2: Endureciendo Docker con Remapeo de Espacios de Nombres de Usuario y mTLS

Esta fase implementa `userns-remap` para un mayor aislamiento del host y configura TLS mutuo (mTLS) para una comunicación segura de la API.

### Paso 2.1: Habilitar el Remapeo de Espacios de Nombres de Usuario (`userns-remap`)

Configura Docker para remapear los privilegios de root de los contenedores a un usuario sin privilegios en el sistema host, reduciendo significativamente la superficie de ataque.

> **Por qué `userns-remap` es Crucial**: Al evitar que el usuario root de un contenedor tenga privilegios de root en el host, mitigas el riesgo de escalada de privilegios si un contenedor se ve comprometido. Este remapeo asigna un rango de UIDs y GIDs sin privilegios al usuario root del contenedor, efectivos solo dentro de su espacio de nombres aislado.

#### Paso 2.1.1: Examinar Mapeos UID/GID Existentes (Opcional)

Puedes inspeccionar los mapeos `subuid` y `subgid` actuales en tu sistema.

```bash
grep -E '^(root|dockremap)' /etc/subuid /etc/subgid
cat /etc/subuid
```

*Justificación*: Estos archivos definen los rangos de UID y GID disponibles para los espacios de nombres de usuario. Después de la configuración, Docker generalmente agregará entradas para un usuario interno `dockremap`.

#### Paso 2.1.2: Modificar `/etc/docker/daemon.json`

Crea o actualiza el archivo de configuración de tu demonio Docker.

```bash
sudo nano /etc/docker/daemon.json
```

Inserta la siguiente configuración:

```json
{
  "userns-remap": "default",
  "experimental": false,
  "storage-driver": "overlay2"
}
```

*Justificación*:
* `"userns-remap": "default"`: Activa la creación automática del usuario `dockremap` y sus rangos de mapeo UID/GID.
* `"experimental": false`: Desactiva las características experimentales potencialmente inestables.
* `"storage-driver": "overlay2"`: Especifica el controlador de almacenamiento `overlay2`, que es recomendado y funciona bien para sistemas Linux.

#### Paso 2.1.3: Reiniciar Docker para Aplicar los Cambios

Un reinicio del demonio es esencial para que `userns-remap` surta efecto. Ten en cuenta que esto invalidará las imágenes y contenedores existentes, que deberán ser reconstruidos o descargados de nuevo.

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

*Justificación*: `daemon-reload` actualiza la configuración de systemd, y `restart docker` aplica las nuevas configuraciones de `daemon.json`.

#### Paso 2.1.4: Confirmar la Activación de `userns-remap`

Verifica que el usuario `dockremap` ha sido creado por Docker.

```bash
getent passwd dockremap
```

*Ejemplo de salida*: `dockremap:x:997:985::/home/dockremap:/bin/sh`

```bash
id dockremap
```

*Ejemplo de salida*: `uid=997(dockremap) gid=985(dockremap) grupos=985(dockremap)`
*Justificación*: Estos comandos confirman la existencia y los detalles del usuario `dockremap`, que Docker utiliza internamente para el remapeo de usuarios.

### Paso 2.2: Implementar TLS Mutuo para la API de Docker

Configura la autenticación criptográfica para tu API de Docker utilizando scripts personalizados y archivos de configuración de OpenSSL del repositorio de GitHub proporcionado.

#### Paso 2.2.1: Preparar el Entorno de Gestión de Certificados

Clona el repositorio necesario que contiene los scripts y las plantillas de OpenSSL en `/opt/docker_conf_m8`.

```bash
# IMPORTANTE: Establece la IP deseada para tu interfaz ficticia de la API de Docker (por ejemplo, 10.254.254.1)
export DOCKER_HOST_IP="TU_IP_HOST_DOCKER_AQUI" # <<< ¡REEMPLAZA ESTE MARCADOR!
BASE_DIR="/opt/docker_conf_m8"

# Clonar el repositorio del proyecto
sudo git clone https://github.com/mano8/docker_conf_m8.git "${BASE_DIR}"
sudo chmod 700 "${BASE_DIR}" # Asegurar el directorio base
```

*Justificación*: Este paso descarga todos los archivos esenciales para la generación de certificados. **Asegúrate de reemplazar `"TU_IP_HOST_DOCKER_AQUI"` con la dirección IP estática que destines a tu interfaz ficticia de la API de Docker.** Esta IP se incrustará en tus certificados de servidor y cliente para una validación segura.

El repositorio `docker_conf_m8` (https://github.com/mano8/docker_conf_m8) contiene:

* **`scripts/validate_docker_host_ip.sh`**: Valida la variable de entorno `DOCKER_HOST_IP`.
    * [Enlace al script](https://github.com/mano8/docker_conf_m8/blob/main/scripts/validate_docker_host_ip.sh)
* **`ssl_conf/ssl_docker_server.conf`**: Plantilla OpenSSL para el certificado de servidor del demonio Docker, ajustado dinámicamente con tu `DOCKER_HOST_IP`.
    * [Enlace a la configuración](https://github.com/mano8/docker_conf_m8/blob/main/ssl_conf/ssl_docker_server.conf)
* **`ssl_conf/ssl_docker_client.conf`**: Plantilla OpenSSL para el certificado de cliente (por ejemplo, para Traefik), también ajustado dinámicamente.
    * [Enlace a la configuración](https://github.com/mano8/docker_conf_m8/blob/main/ssl_conf/ssl_docker_client.conf)
* **`scripts/manage_docker_certs.sh`**: El script principal para automatizar la generación de certificados CA, de servidor y de cliente, incluida la gestión de permisos.
    * [Enlace al script](https://github.com/mano8/docker_conf_m8/blob/main/scripts/manage_docker_certs.sh)

#### Paso 2.2.2: Iniciar la Generación de Certificados

Ejecuta el script principal para generar todos los activos mTLS necesarios.

```bash
sudo "${BASE_DIR}/scripts/manage_docker_certs.sh" generate
```

*Justificación*: Este comando orquesta la creación de:
* **Certificados de Servidor**: `ca.pem`, `server-key.pem`, `server-cert.pem` ubicados en `/etc/docker/certs/` (para el propio demonio Docker).
* **Certificados de Cliente**: `ca.pem`, `client-key.pem`, `client-cert.pem` almacenados en `/opt/docker_conf_m8/certs/` (para aplicaciones cliente seguras como Traefik).
El directorio de certificados de cliente tendrá la propiedad correcta del usuario `dockremap` para compatibilidad con el remapeo de espacios de nombres de usuario.

## 3. Configurar la Interfaz Ficticia

Para configurar la interfaz ficticia `docker0`, es crucial determinar qué sistema de gestión de red utiliza tu sistema. Los métodos varían principalmente según tu distribución (Debian, Ubuntu, Linux Mint) y su propósito (servidor o escritorio).

**Muy Importante:** Debes elegir **SOLO UN** método a continuación para configurar la interfaz `docker0`. El uso de múltiples métodos para la misma interfaz puede provocar conflictos y un comportamiento de red impredecible.

Para ayudarte a elegir, aquí están los escenarios más comunes:

* **Netplan:** Estándar en **servidores Ubuntu** e **instalaciones modernas de Ubuntu Desktop**. Es una capa de abstracción que genera la configuración para `systemd-networkd` (por defecto) o `NetworkManager`.
    * *Comprobación Rápida:* Busca un archivo YAML en `/etc/netplan/` (por ejemplo, `01-netcfg.yaml`).
* **NetworkManager:** Estándar en la mayoría de los **sistemas de escritorio (Ubuntu Desktop, Linux Mint, Debian Desktop)**, ofreciendo gestión dinámica de la red y una interfaz gráfica.
    * *Comprobación Rápida:* Ejecuta `systemctl is-active NetworkManager` (debería mostrar `active`) y `nmcli general status`.
* **`ifupdown`:** El sistema tradicional en las **instalaciones de Debian Server** (y algunas versiones antiguas de Ubuntu) donde las configuraciones se realizan directamente en `/etc/network/interfaces`.
    * *Comprobación Rápida:* Busca configuraciones específicas en `/etc/network/interfaces`.

Una vez que hayas identificado el gestor de red más probable para tu sistema, sigue los pasos de la sección correspondiente.

### 3.1. Configurar Interfaz Ficticia con Netplan (Para Sistemas que Usan Netplan)

Sigue estos pasos si has determinado que tu sistema utiliza **Netplan**. **Si ya has creado archivos directos de `systemd-networkd` (por ejemplo, en `/etc/systemd/network/`) para esta interfaz, elimínalos antes de continuar para evitar conflictos.**

#### 3.1.1. Crear la Configuración de Netplan para `docker0`

Crea un nuevo archivo YAML de Netplan.

```bash
sudo nano /etc/netplan/99-docker-dummy-interface.yaml
```

Pega el siguiente contenido. Ajusta `10.254.254.1/24` si tu `DOCKER_HOST_IP` difiere.

```yaml
network:
  version: 2
  renderer: networkd # Para servidores, 'networkd' suele ser el backend preferido. Para escritorios donde NetworkManager gestiona todo, podrías considerar 'NetworkManager'.
  netdevs:
    docker0:
      kind: dummy
  ethernets:
    docker0:
      addresses: [10.254.254.1/24]
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8] # Opcional: añadir servidores DNS
```

*Explicación*:
* `version: 2`: Especifica la versión de la configuración de Netplan.
* `renderer: networkd`: Indica a Netplan que use `systemd-networkd` como su backend. Elige `NetworkManager` si es tu gestor principal para todas las interfaces y quieres que también gestione esta interfaz ficticia.
* `netdevs`: Define el dispositivo de red virtual `docker0` como una interfaz ficticia.
* `ethernets`: Configura la interfaz `docker0` con la dirección IP estática. Asegúrate de que esta IP coincida con la `DOCKER_HOST_IP` de tus certificados.

#### 3.1.2. Aplicar la Configuración de Netplan

Primero, verifica la configuración en busca de errores de sintaxis.

```bash
sudo netplan try
```

Si `netplan try` no informa de errores, aplica la configuración permanentemente.

```bash
sudo netplan apply
```

*Explicación*: `netplan try` valida tu configuración e intenta aplicarla temporalmente. `netplan apply` aplica los cambios de forma permanente, generando los archivos de backend necesarios y reiniciando el servicio apropiado.

### 3.2. Configurar Interfaz Ficticia con NetworkManager (Para Sistemas que Usan NetworkManager)

Sigue estos pasos si has determinado que tu sistema utiliza **NetworkManager** (por ejemplo, Linux Mint, Ubuntu Desktop, Debian Desktop).

#### 3.2.1. Crear la Interfaz Ficticia `docker0` y la Conexión de NetworkManager

Usa `nmcli` para crear una nueva conexión de tipo "dummy" llamada `docker0` y asignarle la dirección IP.

```bash
# Crear la interfaz dummy
sudo nmcli connection add type dummy con-name docker0 ifname docker0

# Configurar la dirección IP para la conexión docker0
sudo nmcli connection modify docker0 ipv4.addresses 10.254.254.1/24 ipv4.method manual

# Opcional: Configurar servidores DNS (si es necesario para esta interfaz)
sudo nmcli connection modify docker0 ipv4.dns "1.1.1.1 8.8.8.8"

# Activar la conexión
sudo nmcli connection up docker0
```

*Explicación*:
* `nmcli connection add type dummy con-name docker0 ifname docker0`: Crea una nueva conexión de NetworkManager de tipo "dummy" con el nombre de conexión `docker0` y el nombre de interfaz `docker0`.
* `nmcli connection modify docker0 ipv4.addresses ... ipv4.method manual`: Establece la dirección IPv4 para la conexión y especifica que se configura manualmente (estática). Asegúrate de que `10.254.254.1/24` coincida con tu `DOCKER_HOST_IP`.
* `nmcli connection modify docker0 ipv4.dns ...`: (Opcional) Añade servidores DNS si la interfaz `docker0` necesita resolver nombres.
* `nmcli connection up docker0`: Activa la nueva conexión, lo que hará que la interfaz `docker0` aparezca con su dirección IP. NetworkManager gestiona la persistencia de esta configuración.

### 3.3. Configurar Interfaz Ficticia con `ifupdown` (Para Sistemas que Usan `/etc/network/interfaces`)

Sigue estos pasos si tu sistema utiliza **`ifupdown`** para la gestión de red, lo cual es común en las instalaciones tradicionales de Debian server donde ni Netplan ni NetworkManager son los gestores principales.

#### 3.3.1. Crear la Interfaz Ficticia Manualmente

Dado que `ifupdown` no puede crear interfaces de tipo "dummy" directamente a través de su archivo de configuración, deberás crearla manualmente y luego hacerla persistente.

```bash
# Crear la interfaz ficticia docker0 (este comando es temporal hasta el reinicio sin la configuración)
sudo ip link add docker0 type dummy
sudo ip link set docker0 up
```

*Explicación*:
* `sudo ip link add docker0 type dummy`: Crea una nueva interfaz de red virtual de tipo "dummy" llamada `docker0`.
* `sudo ip link set docker0 up`: Activa la interfaz `docker0`.

#### 3.3.2. Hacer la Interfaz Persistente a través de `/etc/network/interfaces`

Edita el archivo de configuración de red principal para asegurar que la interfaz `docker0` se cree y configure al inicio.

```bash
sudo nano /etc/network/interfaces
```

Añade las siguientes líneas al final del archivo. Asegúrate de que la IP `10.254.254.1` coincida con tu `DOCKER_HOST_IP`.

```
# Configuración para la interfaz ficticia de la API de Docker
auto docker0
iface docker0 inet static
  pre-up ip link add docker0 type dummy || true
  address 10.254.254.1
  netmask 255.255.255.0
  post-down ip link del docker0 || true
```

*Explicación*:
* `auto docker0`: Indica que la interfaz `docker0` debe activarse automáticamente al inicio.
* `iface docker0 inet static`: Define `docker0` como una interfaz con una configuración IP estática.
* `pre-up ip link add docker0 type dummy || true`: Este comando se ejecuta antes de que se active la interfaz. Crea la interfaz ficticia si aún no existe. El `|| true` se usa para evitar que el comando falle si la interfaz ya existe (por ejemplo, si ya la creaste manualmente).
* `address 10.254.254.1` y `netmask 255.255.255.0`: Asignan la dirección IP y la máscara de subred a la interfaz.
* `post-down ip link del docker0 || true`: Este comando se ejecuta cuando la interfaz se desactiva, eliminando la interfaz ficticia.

#### 3.3.3. Aplicar la Configuración

Para aplicar la nueva configuración sin reiniciar el sistema (lo cual suele ser necesario con `ifupdown`), puedes intentar desactivar y luego volver a activar la interfaz.

```bash
sudo ifdown docker0
sudo ifup docker0
```

*Nota*: En algunos sistemas o configuraciones, un reinicio completo del servicio de red (`sudo systemctl restart networking` o un reinicio del servidor) puede ser necesario para que los cambios surtan efecto por completo.

*Importante*: Si estás utilizando `ifupdown`, asegúrate de que `NetworkManager` no esté activo para esta interfaz, y que Netplan no esté configurado para gestionarla, para evitar conflictos. La gestión de diferentes interfaces por diferentes herramientas es posible, pero añade complejidad.

### 3.4. Verificar el Estado de `docker0` (Aplicable a todos los métodos)

Independientemente del método que hayas utilizado para configurar la interfaz ficticia, verifica si `docker0` está activa y tiene la IP correcta.

```bash
ip addr show docker0
```

*Salida Esperada*: Similar a las secciones anteriores, mostrando `docker0` con `inet 10.254.254.1/24`.

## Fase 4: Vincular el Demonio Docker a mTLS e Implementar la Seguridad de UFW

Configura el demonio Docker para usar la interfaz ficticia segura con mTLS, luego añade reglas de UFW para el aislamiento de red.

### Paso 4.1: Actualizar la Configuración del Demonio Docker para mTLS

Vuelve a abrir `/etc/docker/daemon.json` para indicarle a Docker que escuche en el punto final TCP seguro y aplique mTLS.

```bash
sudo nano /etc/docker/daemon.json
```

Ajusta el archivo para incluir los parámetros `hosts` y `tls*`, manteniendo tus configuraciones existentes de `userns-remap` y `storage-driver`.

```json
{
  "userns-remap": "default",
  "experimental": false,
  "storage-driver": "overlay2",
  "hosts": ["unix:///var/run/docker.sock", "tcp://10.254.254.1:2376"],
  "tlsverify": true,
  "tlscacert": "/etc/docker/certs/ca.pem",
  "tlscert": "/etc/docker/certs/server-cert.pem",
  "tlskey": "/etc/docker/certs/server-key.pem"
}
```

*Justificación*:
* `"hosts"`: Define que Docker escuchará tanto en el socket Unix local (para acceso directo por CLI) como en el puerto TCP seguro 2376 de la interfaz ficticia `10.254.254.1`.
* `"tlsverify": true`: Fuerza el TLS mutuo, lo que significa que tanto el servidor como el cliente deben presentar y verificar certificados válidos.
* `"tlscacert"`, `"tlscert"`, `"tlskey"`: Especifican las rutas al certificado de la Autoridad de Certificación, al certificado del servidor y a la clave privada del servidor, respectivamente.

### Paso 4.2: Reiniciar el Demonio Docker

Reinicia Docker para cargar las configuraciones actualizadas de la API y TLS.

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

*Justificación*: Esto recarga las configuraciones de systemd y reinicia Docker, aplicando las nuevas configuraciones de `daemon.json`.

### Paso 4.3: Verificar la Conexión TLS Segura Remota

Prueba la conexión mTLS desde tu host usando la interfaz de línea de comandos de Docker y los certificados de cliente.

#### Paso 4.3.1: Establecer Variables de Entorno de Docker

Configura el entorno de tu shell para que apunte a tus certificados de cliente y al punto final seguro de la API de Docker.

```bash
export DOCKER_TLS_VERIFY="1"
export DOCKER_CERT_PATH="/opt/docker_conf_m8/certs"
export DOCKER_HOST="tcp://10.254.254.1:2376"
```

*Justificación*: Estas variables indican a la CLI de Docker que se conecte a través de TLS, verifique los certificados y localice tus credenciales de cliente.

#### Paso 4.3.2: Ejecutar un Comando de Prueba

Intenta un comando básico de Docker para confirmar la conectividad.

```bash
docker ps
```

*Salida Esperada*: Una lista de contenedores en ejecución (posiblemente vacía) sin errores de negociación TLS.
*Justificación*: Una ejecución exitosa confirma que tu CLI de Docker puede comunicarse de forma segura con el demonio Docker a través del punto final TCP seguro con mTLS.

## Fase 5: Endurecimiento del Acceso a la Red con UFW

Configura UFW para crear un entorno altamente restringido para tu API de Docker.

**ADVERTENCIA DE SEGURIDAD CRÍTICA**: Al activar UFW, es absolutamente esencial permitir el tráfico SSH *antes* de activar el cortafuegos, de lo contrario ¡corres el riesgo de perder la conectividad remota con tu servidor!

### Paso 5.1: Permitir Acceso SSH (Prerrequisito Crucial)

Permite las conexiones SSH entrantes para evitar el bloqueo.

```bash
sudo ufw allow ssh comment 'Permitir acceso SSH'
# Si tu servidor SSH se ejecuta en un puerto no estándar (por ejemplo, 2222), usa:
# sudo ufw allow 2222/tcp comment 'Permitir SSH en puerto personalizado'
```

*Justificación*: Esta regla permite explícitamente las conexiones SSH entrantes, evitando que te quedes bloqueado cuando el cortafuegos esté activado.

### Paso 5.2: Establecer Políticas Predeterminadas del Cortafuegos

Define los comportamientos predeterminados de UFW para el tráfico entrante y saliente, luego activa el cortafuegos.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw enable
```
