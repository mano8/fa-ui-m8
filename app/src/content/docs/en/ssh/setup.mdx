## SSH Authentication Keys

### Generate New Public/Private Key Pairs

On the client machine, open the command prompt in your `.ssh` directory located in your HOME.

```bash
ssh-keygen -t ed25519 -C "MyComment" -a 100 -f ~/.ssh/MySshKeyName
Enter passphrase (empty for no passphrase):
```

> 👉 Set a strong passphrase to protect your key

| Option | Description |
|--------|-------------|
| `-t` | Key algorithm used |
| `-C` | Comment can help to identify the key |
| `-a` | Key derivation function (KDF) rounds/iterations (16 by default) |

This will create two keys in your current folder:
- **MySshKeyName**: The private key (never to be shared)
- **MySshKeyName.pub**: The public key (can be shared)

#### Secure Private Key

👉 Only the user owner must be authorized to read and write.

* **On Linux**

```bash
chmod 600 ~/.ssh/MySshKeyName
# Verify new access rights
ls -alt ~/.ssh/MySshKeyName
```

* **On Windows**

First, remove inheritance from the `.ssh` folder

```bash
Icacls $env:USERPROFILE\.ssh /c /t /Inheritance:d
```

```bash
Icacls $env:USERPROFILE\.ssh\MySshKeyName /c /t /Remove:g "Tout le monde" Administrateurs System
# Verify new access rights
Icacls $env:USERPROFILE\.ssh\MySshKeyName
```

#### Copy the Public Key to the Server

We need to copy the public key to the server's `authorized_keys` file.
👉 Located in the server `<SSH_USER>` home directory.

* **On Linux**

```bash
ssh-copy-id -i ~/.ssh/MySshKeyName.pub <SSH_USER>@<SSH_HOST>
```

* **On Windows**

On Windows, we can't use `ssh-copy-id`, but we can use the above one-liner command or copy the key via SFTP.

```bash
type $env:USERPROFILE\.ssh\MySshKeyName.pub | ssh <SSH_USER>@<SSH_HOST> "cat >> .ssh/authorized_keys"
```

### Test Connection with SSH Key

```bash
ssh -i ~/.ssh/MySshKeyName <SSH_USER>@<SSH_HOST>
```

### Update Passphrase

```bash
ssh-keygen -p -P <OldPassphrase> -N <NewPassphrase> -f <PrivateKey>
```

Example:

```bash
ssh-keygen -p -P 'Y27SH19HDIWD' -N 'azerty123' -f private-8297.key
```

## Set Alias on SSH Config

We can create SSH aliases in the `~/.ssh/config` file on the client machine.

> 👉 See [Man Page](http://man.openbsd.org/OpenBSD-current/man5/ssh_config.5 "Man Page")

```text
# Global Configuration
Host *
    IgnoreUnknown AddKeysToAgent,UseKeychain
    UseKeychain yes
    # Specifies whether keys should be automatically added to a running ssh-agent(1)
    AddKeysToAgent yes

# Alias Configuration
Host MyAlias
    HostName IP_ADDRESS_OR_FQDN
    Port SSH_SERVER_PORT
    User SSH_USER
    IdentitiesOnly yes # Use only ssh key
    IdentityFile ~/.ssh/MySshKeyName # private ssh key path
```

### Secure Config File

* **On Linux**

```bash
chmod 600 ~/.ssh/config
# Verify new access rights
ls -alt ~/.ssh/config
```

* **On Windows**

👉 If not executed in previous steps, remove inheritance from the `.ssh` folder

```bash
Icacls $env:USERPROFILE\.ssh /c /t /Inheritance:d
```

```bash
Icacls $env:USERPROFILE\.ssh\config /c /t /Remove:g "Tout le monde" Administrateurs System
# Verify new access rights
Icacls $env:USERPROFILE\.ssh\config
```

### Connect to the Server Using Alias

```bash
ssh MyAlias
```

## Secure SSH Server

On the SSH server, the configuration file is located in `/etc/ssh/sshd_config`.
The default configuration is not fully secure; you need to apply some changes.

### Secure SSH Directly on `sshd_config`

1. Create a copy of the original configuration

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.back
```

2. Edit the configuration file

```bash
sudo nano /etc/ssh/sshd_config
```

### Add Config File to `sshd_config.d`

Instead of changing the configuration directly in `/etc/ssh/sshd_config`, a best practice is to set up a new configuration by adding a new file directly in the `/etc/ssh/sshd_config.d` directory.

```bash
sudo nano /etc/ssh/sshd_config.d/hardening.conf
```

### Recommended Security Updates

| Key | Recommended Value | Description |
|---------|-------------|-------------|
| `Protocol` | `2` | To lock SSH protocol to the current secure version. |
| `Port` | `[SSH_PORT]` | To change the SSH port (default is 22, but all bots scan this port by default; replace `[SSH_PORT]` with a valid and unused port). |
| `LogLevel` | `VERBOSE` | Add verbose logs on `/var/log/auth.log` to detect suspicious activity. |
| `MaxAuthTries` | `3` | Limit max login attempts. |
| `MaxSessions` | `10` | Limit max opened sessions. |
| `PermitRootLogin` | `no` | Disable root login on the SSH server. |
| `AllowUsers` | `[my_user1, my_user2]` | Limit users who can connect to the SSH server (adapt `[my_user1, my_user2]` to your use case). |
| `StrictModes` | `yes` | Ensure file and directory permissions before allowing a user to log in. It's a security feature.. |
| `LoginGraceTime` | `40` | Max time to login on the SSH server. |
| `PasswordAuthentication` | `no` | Disable password authentication (be sure you have correctly set up your SSH keys). |
| `ChallengeResponseAuthentication` | `no` | Disable challenge-response passwords. |
| `AllowAgentForwarding` | `no` | Disable SSH agent forwarding. |
| `UsePAM` | `yes` | Enable PAM authentication. |
| `PermitTunnel` | `no` | Disable SSH tunneling. |
| `X11Forwarding` | `no` | Disable SSH X11 forwarding. |
| `ClientAliveInterval` | `0` | |
| `ClientAliveCountMax` | `2` | Close connection after 2 failed requests. |

### Config example

This an example of SSH configuration, you will must adapt to your own needs:

* **`hardening.conf`**:
    
    ```bash
    sudo nano /etc/ssh/sshd_config.d/hardening.conf
    ```

    ```ini
    Protocol 2

    Port 60124

    LogLevel VERBOSE

    PermitRootLogin no
    AllowUsers zino
    StrictModes yes
    MaxAuthTries 3
    MaxSessions 10

    PubkeyAuthentication yes
    PasswordAuthentication no
    PermitEmptyPasswords no

    ChallengeResponseAuthentication no
    KbdInteractiveAuthentication no
    UsePAM yes

    AllowAgentForwarding no
    PermitTunnel no
    X11Forwarding no

    ClientAliveInterval 0
    ClientAliveCountMax 2

    # DoS protection
    MaxStartups 2:30:10
    LoginGraceTime 40
    ```

* **cyphers.conf**:

    ```bash
    sudo nano /etc/ssh/sshd_config.d/cyphers.conf
    ```

    ```ini
    # Restrict key exchange, cipher, and MAC algorithms, as per sshaudit.com
    # hardening guide.
    KexAlgorithms sntrup761x25519-sha512,sntrup761x25519-sha512@openssh.com,curve25519-sha256,curve25519-sha256@libssh.org,gss-curve25519-sha256-,diffie-hellman-group16-sha512,gss-group16-sha512-,diffie-hellman-group18-sha512,diffie-hellman-group-exchange-sha256

    Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes256-ctr,aes192-ctr,aes128-gcm@openssh.com,aes128-ctr

    MACs hmac-sha2-256-etm@openssh.com,hmac-sha2-512-etm@openssh.com,umac-128-etm@openssh.com

    HostKeyAlgorithms sk-ssh-ed25519-cert-v01@openssh.com,ssh-ed25519-cert-v01@openssh.com,rsa-sha2-512-cert-v01@openssh.com,rsa-sha2-256-cert-v01@openssh.com,sk-ssh-ed25519@openssh.com,ssh-ed25519,rsa-sha2-512,rsa-sha2-256

    RequiredRSASize 3072

    CASignatureAlgorithms sk-ssh-ed25519@openssh.com,ssh-ed25519,rsa-sha2-512,rsa-sha2-256

    GSSAPIKexAlgorithms gss-curve25519-sha256-,gss-group16-sha512-

    HostbasedAcceptedAlgorithms sk-ssh-ed25519-cert-v01@openssh.com,ssh-ed25519-cert-v01@openssh.com,sk-ssh-ed25519@openssh.com,ssh-ed25519,rsa-sha2-512-cert-v01@openssh.com,rsa-sha2-512,rsa-sha2-256-cert-v01@openssh.com,rsa-sha2-256

    PubkeyAcceptedAlgorithms sk-ssh-ed25519-cert-v01@openssh.com,ssh-ed25519-cert-v01@openssh.com,sk-ssh-ed25519@openssh.com,ssh-ed25519,rsa-sha2-512-cert-v01@openssh.com,rsa-sha2-512,rsa-sha2-256-cert-v01@openssh.com,rsa-sha2-256
    ```

### Apply Changes

👉 Try the new configuration to ensure there are no errors

```bash
sudo sshd -t
```

Then apply changes

```bash
sudo systemctl reload sshd
sudo systemctl restart sshd
```

👉 Control new configuration

```bash
sudo sshd -T
```

## Send Files Over SSH with SCP

**Securely transfer your files** between local and remote systems,  
or even directly between two remote servers, using the `scp` (Secure Copy Protocol) command.  
`scp` leverages SSH for data transfer and authentication, ensuring your files are always encrypted in transit.

| Command | Description |
|---------|-------------|
| `scp <LocalFilePath> <sshUser>@<targetIP>:<TargetPath> -P <SshPort>` | **Upload a file** from your local machine to a remote server. This is perfect for deploying configurations or moving data to your server. |
| `scp <sshUser>@<targetIP>:<RemoteFilePath> -P <SshPort> <LocalPath>` | **Download a file** from a remote server to your local machine. Use this to retrieve logs, backups, or project files from your servers. |
| `scp <sshUser1>@<targetIP1>:<RemoteFilePath> <sshUser2>@<targetIP2>:<RemoteFilePath>` | **Directly transfer a file from one remote server to another.** This command initiates a transfer where `server1` sends the file directly to `server2`, without routing it through your local machine. |

> 👉 **Remember:**  
> If you don't provide an absolute path for either the source or destination,  
> `scp` will default to using the current user's **home directory (`~/`)** on the respective system.

### Key `scp` Options:

Enhance your `scp` transfers with these useful options:

| Option | Description |
|---------|-------------|
| `-r` | **Recursively copy entire directories.** Essential for moving folders and their contents. |
| `-P <SshPort>` | **Specify the SSH port** if your remote server isn't using the default port 22. |
| `-p` | **Preserve original file attributes** like modification times, access times, and permissions. Great for maintaining data integrity. |
| `-q` | **Run in quiet mode.** Suppresses the progress meter and non-error messages, ideal for scripting. |
| `-C` | **Enable compression.** Compresses files during transfer, which can speed up transfers over slow network connections, especially for text files. |
| `-l <Limit>` | **Limit the bandwidth** used by `scp`. Specify in kilobits per second (Kbps) to prevent `scp` from saturating your network. |
| `-v` | **Activate verbose mode.** Displays detailed debugging information about the `scp` process, helpful for troubleshooting connection issues. |

## Port Forwarding

### Static Port Forwarding

```bash
ssh -L <LocalPort>:<TargetForwardIp>:<TargetForwardPort> <sshUser>@<targetIP> -p <SshPort>
```

In the above example, the target machine has a service accessible locally on `127.0.0.1:8080`. To access this service from the local machine, execute port forwarding via SSH. This will make the local service from the target machine (`127.0.0.1:8080`) accessible on the local machine on `127.0.0.1:9001`.

```bash
ssh -L 9001:127.0.0.1:8080 matthew@10.10.11.245
```

### Dynamic Port Forwarding

Instead of local port forwarding, we could also opt for dynamic port forwarding, again using SSH. Unlike local port forwarding and remote port forwarding, which use a specific local and remote port (we used `9001` and `8080`, for instance), dynamic port forwarding uses a single local port and dynamically assigns remote ports for each connection.

```bash
ssh -D 9001 matthew@10.10.11.245
```

To make use of dynamic port forwarding, a tool such as proxychains is especially useful. In summary, and as the name implies, proxychains can be used to tunnel a connection through multiple proxies; a use case for this could be increasing anonymity, as the origin of a connection would be significantly more difficult to trace. In our case, we would only tunnel through one such "proxy"; the target machine.

#### Install Proxychains

```bash
sudo apt-get update
sudo apt-get install proxychains
```

#### Configure Proxychains

You have the option to select any editor that you like. For this example, we are using nano, but there are other alternatives such as vim, gedit, leafpad, or sublime.

Command:

```bash
sudo nano /etc/proxychains4.conf
```

The minimal changes that we have to make to the file for proxychains to work in our current use case are to:

1. Ensure that `strict_chain` is not commented out (dynamic_chain and random_chain should be commented out).
2. At the very bottom of the file, under `[ProxyList]`, we specify the socks5 (or socks4) host and port that we used for our tunnel.

In our case, it would look something like this, as our tunnel is listening at `localhost:9001`.

```text
<SNIP>
[ProxyList]
# add proxy here ...
# meanwile
# defaults set to "tor"
#socks4 127.0.0.1 9050
socks5 127.0.0.1 9001
```

Having configured proxychains correctly, we can now connect to any service on the target as if we were on the target machine ourselves! This is done by prefixing whatever command we want to run with proxychains, like so:

Example for accessing `PostgreSQL` service:

```bash
proxychains psql -U toto -h localhost -p 5432
```
