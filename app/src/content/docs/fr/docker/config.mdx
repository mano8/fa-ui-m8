Dans le monde conteneurisé d'aujourd'hui, sécuriser l'API de votre démon Docker est primordial, surtout lorsque vous orchestrez des services comme des proxys inverses (par exemple, Traefik) sur le même hôte. Bien que Docker offre une flexibilité incroyable, ses configurations par défaut peuvent exposer votre environnement à des risques inutiles. Cet article explore une architecture de sécurité robuste qui marie les fonctionnalités natives de Docker avec des techniques de durcissement réseau pour créer une défense impénétrable autour de votre écosystème de conteneurs.

Ce plan de sécurité avancé intègre :

- **Remappage d'Espaces de Noms Utilisateur (`userns-remap`)** : Un mécanisme d'isolation fondamental qui prive les conteneurs des véritables privilèges root sur l'hôte.
- **Interface Réseau Factice (Dummy Interface)** : La création d'un segment réseau dédié et interne pour votre API Docker, éloigné de toute portée externe.
- **TLS Mutuel (mTLS)** : L'implémentation d'une couche puissante d'authentification et de chiffrement bidirectionnelle pour toutes les communications API.
- **Pare-feu Simple (UFW)** : La définition stratégique de règles réseau pour autoriser uniquement le trafic interne et autorisé vers le point d'accès API.

## L'Impératif d'une Sécurité Renforcée de l'API Docker

Traditionnellement, exposer l'API Docker sur un port TCP standard sans authentification robuste constitue une vulnérabilité significative. Même en utilisant `userns-remap` pour l'exécution de conteneurs sans root, le point d'accès API lui-même peut rester un vecteur d'attaque pour d'autres processus ou des conteneurs compromis sur la même machine.

De plus, la pratique courante de monter directement `/var/run/docker.sock` dans les conteneurs, bien que pratique pour des outils comme Traefik, comporte des risques inhérents. Une faille dans un tel conteneur pourrait donner à un attaquant le contrôle total de votre démon Docker, lui permettant de lancer des conteneurs malveillants ou de perturber l'ensemble de votre infrastructure.

Notre solution proposée aborde méticuleusement ces préoccupations en :

- **Éliminant le Montage Direct du Socket** : Faisant passer les clients comme Traefik à une communication via un point d'accès TCP au lieu d'un accès direct au socket.
- **Créant une Passerelle API Isolée** : Liant l'API Docker à une interface factice virtuelle, garantissant qu'elle n'est jamais directement exposée aux réseaux externes.
- **Appliquant une Authentification Stricte** : Employant mTLS pour exiger une vérification cryptographique pour le client (par exemple, Traefik) et le démon Docker, garantissant que seules les entités fiables peuvent interagir.
- **Construisant une Défense Multi-Couches** : Combinant le remappage d'utilisateurs, la segmentation réseau, un chiffrement fort et le pare-feu pour créer une posture de sécurité résiliente.

## Phase 1 : Établir la Fondation Docker

Cette phase initiale se concentre sur [l'installation du moteur Docker](https://docs.docker.com/engine/install/ubuntu/) et la configuration de la sécurité de base via le remappage des espaces de noms d'utilisateurs sur votre serveur Ubuntu.

### Étape 1.1 : Supprimer les Paquets Docker Obsoletes

Commencez par supprimer méticuleusement toutes les installations Docker précédentes ou conflictuelles pour assurer une base propre.

```bash
for pkg in docker.io docker-doc docker-compose docker-compose-v2 podman-docker containerd runc; do sudo apt-get remove $pkg; done
```

_Justification_ : Ce nettoyage préventif empêche les conflits potentiels et assure une installation sans accroc du moteur Docker officiel.

### Étape 1.2 : Installer Docker Engine

#### Étape 1.2.1 : Intégrer le Dépôt APT Officiel de Docker

Mettez en place le dépôt APT officiel de Docker pour garantir l'accès aux versions stables les plus récentes de Docker.

```bash
# Récupérer la clé GPG officielle de Docker :
sudo apt-get update
sudo apt-get install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Ajouter le dépôt aux sources Apt :
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
```

_Justification_ : Cette séquence de commandes garantit que votre système peut télécharger et vérifier en toute sécurité les paquets Docker directement depuis la source officielle.

#### Étape 1.2.2 : Déployer les Composants Essentiels de Docker

Installez les composants essentiels de Docker qui constituent le moteur.

```bash
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

_Justification_ : Cette commande installe le démon Docker Community Edition, son interface en ligne de commande, le runtime `containerd`, et des plugins vitaux pour la construction et l'orchestration de conteneurs.

### Étape 1.3 : Vérifier le Statut Opérationnel de Docker

Confirmez que votre installation Docker est entièrement fonctionnelle.

```bash
sudo docker run hello-world
```

_Justification_ : L'exécution de l'image `hello-world` est un moyen rapide et efficace de confirmer que le démon Docker est en cours d'exécution et réactif.

## Phase 2 : Renforcer Docker avec le Remappage d'Espaces de Noms Utilisateur et mTLS

Cette phase met en œuvre [`userns-remap`](https://docs.docker.com/engine/security/userns-remap/) pour une isolation accrue de l'hôte et configure le TLS mutuel (mTLS) pour une communication API sécurisée.

### Étape 2.1 : Activer le Remappage d'Espaces de Noms Utilisateur (`userns-remap`)

Configurez Docker pour remapper les privilèges root des conteneurs à un utilisateur non privilégié sur le système hôte, réduisant ainsi considérablement la surface d'attaque.

> **Pourquoi `userns-remap` est crucial** : En empêchant l'utilisateur root d'un conteneur d'avoir des privilèges root sur l'hôte, vous atténuez le risque d'escalade de privilèges si un conteneur est compromis. Ce remappage attribue une plage d'UID et de GID non privilégiés à l'utilisateur root du conteneur, efficaces uniquement dans son espace de noms isolé.

#### Étape 2.1.1 : Examiner les Mappages UID/GID Existants (Facultatif)

Vous pouvez inspecter les mappages `subuid` et `subgid` actuels sur votre système.

```bash
grep -E '^(root|dockremap)' /etc/subuid /etc/subgid
cat /etc/subuid
```

_Justification_ : Ces fichiers définissent les plages d'UID et de GID disponibles pour les espaces de noms d'utilisateurs. Après la configuration, Docker ajoutera généralement des entrées pour un utilisateur interne `dockremap`.

#### Étape 2.1.2 : Modifier `/etc/docker/daemon.json`

Créez ou mettez à jour le fichier de configuration de votre démon Docker.

```bash
sudo nano /etc/docker/daemon.json
```

Insérez la configuration suivante :

```json
{
  "userns-remap": "default",
  "experimental": false,
  "storage-driver": "overlay2"
}
```

_Justification_ :

- `"userns-remap": "default"` : Active la création automatique de l'utilisateur `dockremap` et de ses plages de mappage UID/GID.
- `"experimental": false` : Désactive les fonctionnalités expérimentales potentiellement instables.
- `"storage-driver": "overlay2"` : Spécifie le pilote de stockage [`overlay2`](https://docs.docker.com/engine/storage/drivers/overlayfs-driver/), recommandé et performant pour les systèmes Linux.

#### Étape 2.1.3 : Redémarrer Docker pour Appliquer les Modifications

Un redémarrage du démon est essentiel pour que `userns-remap` prenne effet. Soyez conscient que cela invalidera les images et conteneurs existants, qui devront être reconstruits ou re-téléchargés.

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

_Justification_ : `daemon-reload` rafraîchit la configuration de systemd, et `restart docker` applique les nouveaux paramètres de `daemon.json`.

#### Étape 2.1.4 : Confirmer l'Activation de `userns-remap`

Vérifiez que l'utilisateur `dockremap` a bien été créé par Docker.

```bash
getent passwd dockremap
```

_Exemple de sortie_ : `dockremap:x:997:985::/home/dockremap:/bin/sh`

```bash
id dockremap
```

_Exemple de sortie_ : `uid=997(dockremap) gid=985(dockremap) groupes=985(dockremap)`
_Justification_ : Ces commandes confirment l'existence et les détails de l'utilisateur `dockremap`, que Docker utilise en interne pour le remappage des utilisateurs.

### Étape 2.2 : Implémenter le TLS Mutuel pour l'API Docker

Configurez l'authentification cryptographique pour votre API Docker à l'aide de scripts personnalisés et de fichiers de configuration OpenSSL du dépôt GitHub fourni.

#### Étape 2.2.1 : Préparer l'Environnement de Gestion des Certificats

Clonez le dépôt nécessaire contenant les scripts et les modèles OpenSSL dans `/opt/docker_conf_m8`.

```bash
# IMPORTANT : Définissez l'IP souhaitée pour votre interface factice Docker API (par exemple, 10.254.254.1)
export DOCKER_HOST_IP="VOTRE_IP_HOTE_DOCKER_ICI" # <<< REMPLACEZ CE PLACEHOLDER !
BASE_DIR="/opt/docker_conf_m8"

# Cloner le dépôt du projet
sudo git clone https://github.com/mano8/docker_conf_m8.git "${BASE_DIR}"
sudo chmod 700 "${BASE_DIR}" # Sécuriser le répertoire de base
```

_Justification_ : Cette étape télécharge tous les fichiers essentiels pour la génération des certificats. **Assurez-vous de remplacer `"VOTRE_IP_HOTE_DOCKER_ICI"` par l'adresse IP statique que vous destinez à votre interface factice Docker API.** Cette IP sera intégrée à vos certificats serveur et client pour une validation sécurisée.

Le dépôt `docker_conf_m8` ([https://github.com/mano8/docker_conf_m8](https://github.com/mano8/docker_conf_m8)) contient :

- **`scripts/validate_docker_host_ip.sh`** : Valide la variable d'environnement `DOCKER_HOST_IP`.
  - [Lien vers le script](https://github.com/mano8/docker_conf_m8/blob/main/scripts/validate_docker_host_ip.sh)
- **`ssl_conf/ssl_docker_server.conf`** : Modèle OpenSSL pour le certificat serveur du démon Docker, ajusté dynamiquement avec votre `DOCKER_HOST_IP`.
  - [Lien vers la configuration](https://github.com/mano8/docker_conf_m8/blob/main/ssl_conf/ssl_docker_server.conf)
- **`ssl_conf/ssl_docker_client.conf`** : Modèle OpenSSL pour le certificat client (par exemple, pour Traefik), également ajusté dynamiquement.
  - [Lien vers la configuration](https://github.com/mano8/docker_conf_m8/blob/main/ssl_conf/ssl_docker_client.conf)
- **`scripts/manage_docker_certs.sh`** : Le script principal pour automatiser la génération des certificats CA, serveur et client, y compris la gestion des permissions.
  - [Lien vers le script](https://github.com/mano8/docker_conf_m8/blob/main/scripts/manage_docker_certs.sh)

#### Étape 2.2.2 : Lancer la Génération des Certificats

Exécutez le script principal pour générer tous les actifs mTLS nécessaires.

```bash
sudo "${BASE_DIR}/scripts/manage_docker_certs.sh" generate
```

_Justification_ : Cette commande orchestre la création de :

- **Certificats Serveur** : `ca.pem`, `server-key.pem`, `server-cert.pem` situés dans `/etc/docker/certs/` (pour le démon Docker lui-même).
- **Certificats Client** : `ca.pem`, `client-key.pem`, `client-cert.pem` stockés dans `/opt/docker_conf_m8/certs/` (pour les applications clientes sécurisées comme Traefik).
  Le répertoire des certificats clients sera correctement possédé par l'utilisateur `dockremap` pour une compatibilité avec le remappage d'espaces de noms utilisateur.

## 3. Configurer l'Interface Factice

Pour configurer l'interface factice `docker0`, il est crucial de déterminer quel est le système de gestion de réseau utilisé par votre système. Les méthodes varient principalement en fonction de votre distribution (Debian, Ubuntu, Linux Mint) et de son objectif (serveur ou bureau).

**Très Important :** Vous devez choisir **UNE SEULE** méthode ci-dessous pour configurer l'interface `docker0`. L'utilisation de plusieurs méthodes pour la même interface peut entraîner des conflits et un comportement réseau imprévisible.

Pour vous aider à choisir, voici les scénarios les plus courants :

* **Netplan :** Standard sur les **serveurs Ubuntu** et les **installations Ubuntu Desktop modernes**. C'est une couche d'abstraction qui génère la configuration pour `systemd-networkd` (par défaut) ou `NetworkManager`.
    * *Vérification rapide :* Cherchez un fichier YAML dans `/etc/netplan/` (par exemple, `01-netcfg.yaml`).
* **NetworkManager :** Standard sur la plupart des **systèmes de bureau (Ubuntu Desktop, Linux Mint, Debian Desktop)**, offrant une gestion dynamique du réseau et une interface graphique.
    * *Vérification rapide :* Exécutez `systemctl is-active NetworkManager` (devrait afficher `active`) et `nmcli general status`.
* **`ifupdown` :** Le système traditionnel sur les **installations Debian Serveur** (et certaines anciennes versions d'Ubuntu) où les configurations sont faites directement dans `/etc/network/interfaces`.
    * *Vérification rapide :* Cherchez des configurations spécifiques dans `/etc/network/interfaces`.

Une fois que vous avez identifié le gestionnaire de réseau le plus probable pour votre système, suivez les étapes de la section correspondante.

### 3.1. Configurer l'Interface Factice avec Netplan (Pour les systèmes utilisant Netplan)

Suivez ces étapes si vous avez déterminé que votre système utilise `Netplan`. **Si vous avez déjà créé des fichiers `systemd-networkd` directs (par exemple, dans `/etc/systemd/network/`) pour cette interface, veuillez les supprimer avant de procéder pour éviter les conflits.**

#### 3.1.1. Créer la Configuration Netplan pour `docker0`

Créez un nouveau fichier YAML Netplan.

```bash
sudo nano /etc/netplan/99-docker-dummy-interface.yaml
```
Collez le contenu suivant. Ajustez `10.254.254.1/24` si votre `DOCKER_HOST_IP` est différent.

```yaml
network:
  version: 2
  renderer: networkd # Pour les serveurs, 'networkd' est généralement le backend préféré. Pour les postes de travail où NetworkManager gère tout, vous pourriez envisager 'NetworkManager'.
  netdevs:
    docker0:
      kind: dummy
  ethernets:
    docker0:
      addresses: [10.254.254.1/24]
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8] # Facultatif : ajoutez des serveurs DNS
```
*Explication* :
* `version: 2` : Spécifie la version de la configuration Netplan.
* `renderer: networkd` : Indique à Netplan d'utiliser `systemd-networkd` comme backend. Choisissez `NetworkManager` si c'est votre gestionnaire principal pour toutes les interfaces et que vous souhaitez qu'il gère également cette interface factice.
* `netdevs` : Définit le périphérique réseau virtuel `docker0` comme une interface factice.
* `ethernets` : Configure l'interface `docker0` avec l'adresse IP statique. Assurez-vous que cette IP correspond à l'`DOCKER_HOST_IP` de vos certificats.

#### 3.1.2. Appliquer la Configuration Netplan

Vérifiez d'abord la configuration pour les erreurs de syntaxe.

```bash
sudo netplan try
```
Si `netplan try` ne signale aucune erreur, appliquez la configuration de manière permanente.

```bash
sudo netplan apply
```
*Explication* : `netplan try` valide votre configuration et tente de l'appliquer temporairement. `netplan apply` applique les modifications de manière permanente, générant les fichiers de backend nécessaires et redémarrant le service approprié.

### 3.2. Configurer l'Interface Factice avec NetworkManager (Pour les systèmes utilisant NetworkManager)

Suivez ces étapes si vous avez déterminé que votre système utilise `NetworkManager` (par exemple, Linux Mint, Ubuntu Desktop, Debian Desktop).

#### 3.2.1. Créer l'Interface Factice `docker0` et la Connexion NetworkManager

Utilisez `nmcli` pour créer une nouvelle connexion de type "dummy" nommée `docker0` et lui attribuer l'adresse IP.

```bash
# Créer l'interface dummy
sudo nmcli connection add type dummy con-name docker0 ifname docker0

# Configurer l'adresse IP pour la connexion docker0
sudo nmcli connection modify docker0 ipv4.addresses 10.254.254.1/24 ipv4.method manual

# Facultatif : Configurer des serveurs DNS (si nécessaire pour cette interface)
sudo nmcli connection modify docker0 ipv4.dns "1.1.1.1 8.8.8.8"

# Mettre la connexion en place
sudo nmcli connection up docker0
```
*Explication* :
* `nmcli connection add type dummy con-name docker0 ifname docker0` : Crée une nouvelle connexion NetworkManager de type "dummy" avec le nom de connexion `docker0` et l'interface physique `docker0`.
* `nmcli connection modify docker0 ipv4.addresses ... ipv4.method manual` : Définit l'adresse IPv4 de la connexion et spécifie qu'elle est configurée manuellement (statique). Assurez-vous que `10.254.254.1/24` correspond à votre `DOCKER_HOST_IP`.
* `nmcli connection modify docker0 ipv4.dns ...` : (Facultatif) Ajoute des serveurs DNS si l'interface `docker0` a besoin de résoudre des noms.
* `nmcli connection up docker0` : Active la nouvelle connexion, ce qui fera apparaître l'interface `docker0` avec son adresse IP. NetworkManager gère la persistance de cette configuration.

### 3.3. Configurer l'Interface Factice avec `ifupdown` (Pour les systèmes utilisant `/etc/network/interfaces`)

Suivez ces étapes si votre système utilise `ifupdown` pour la gestion du réseau, ce qui est courant sur les installations Debian serveur traditionnelles où ni Netplan ni NetworkManager ne sont les gestionnaires principaux.

#### 3.3.1. Créer l'Interface Factice Manuellement

Puisque `ifupdown` ne peut pas créer d'interfaces de type "dummy" directement via son fichier de configuration, vous devrez la créer manuellement et la rendre persistante.

```bash
# Créer l'interface factice docker0 (cette commande est temporaire jusqu'au redémarrage sans la config)
sudo ip link add docker0 type dummy
sudo ip link set docker0 up
```
*Explication* :
* `sudo ip link add docker0 type dummy` : Crée une nouvelle interface réseau virtuelle de type "dummy" nommée `docker0`.
* `sudo ip link set docker0 up` : Active l'interface `docker0`.

#### 3.3.2. Rendre l'Interface Persistante via `/etc/network/interfaces`

Éditez le fichier de configuration réseau principal pour que l'interface `docker0` soit créée et configurée au démarrage.

```bash
sudo nano /etc/network/interfaces
```
Ajoutez les lignes suivantes à la fin du fichier. Assurez-vous que l'IP `10.254.254.1` correspond à votre `DOCKER_HOST_IP`.

```
# Configuration de l'interface factice Docker API
auto docker0
iface docker0 inet static
  pre-up ip link add docker0 type dummy || true
  address 10.254.254.1
  netmask 255.255.255.0
  post-down ip link del docker0 || true
```
*Explication* :
* `auto docker0` : Indique que l'interface `docker0` doit être activée automatiquement au démarrage.
* `iface docker0 inet static` : Définit `docker0` comme une interface avec une configuration IP statique.
* `pre-up ip link add docker0 type dummy || true` : Cette commande s'exécute avant que l'interface ne soit activée. Elle crée l'interface factice si elle n'existe pas déjà. Le `|| true` est utilisé pour empêcher l'échec de la commande si l'interface existe déjà (par exemple, si vous l'avez déjà créée manuellement).
* `address 10.254.254.1` et `netmask 255.255.255.0` : Attribuent l'adresse IP et le masque de sous-réseau à l'interface.
* `post-down ip link del docker0 || true` : Cette commande s'exécute lorsque l'interface est désactivée, supprimant l'interface factice.

#### 3.3.3. Appliquer la Configuration

Pour appliquer la nouvelle configuration sans redémarrer le système (ce qui est souvent nécessaire avec `ifupdown`), vous pouvez essayer de désactiver puis réactiver l'interface.

```bash
sudo ifdown docker0
sudo ifup docker0
```
*Note* : Sur certains systèmes ou configurations, un redémarrage complet du service réseau (`sudo systemctl restart networking` ou un redémarrage du serveur) peut être nécessaire pour que les modifications prennent pleinement effet.

*Important* : Si vous utilisez `ifupdown`, assurez-vous que `NetworkManager` n'est pas actif pour cette interface, et que Netplan n'est pas configuré pour la gérer, afin d'éviter les conflits. La gestion de différentes interfaces par différents outils est possible, mais cela ajoute de la complexité.

### 3.4. Vérifier le Statut de `docker0` (Applicable à toutes les méthodes)

Quelle que soit la méthode que vous avez utilisée pour configurer l'interface factice, vérifiez si `docker0` est active et possède la bonne adresse IP.

```bash
ip addr show docker0
```
*Exemple de sortie attendue* : Similaire aux sections précédentes, montrant `docker0` avec `inet 10.254.254.1/24`.

## Phase 4 : Lier le Démon Docker à mTLS et Implémenter la Sécurité UFW

Configurez le démon Docker pour utiliser l'interface factice sécurisée avec mTLS, puis ajoutez des règles UFW pour l'isolation du réseau.

### Étape 4.1 : Mettre à Jour la Configuration du Démon Docker pour mTLS

Rouvrez `/etc/docker/daemon.json` pour indiquer à Docker d'écouter sur le point d'accès TCP sécurisé et d'appliquer mTLS.

```bash
sudo nano /etc/docker/daemon.json
```

Ajustez le fichier pour inclure les paramètres `hosts` et `tls*`, en conservant vos paramètres `userns-remap` et `storage-driver`.

```json
{
  "userns-remap": "default",
  "experimental": false,
  "storage-driver": "overlay2",
  "hosts": ["unix:///var/run/docker.sock", "tcp://10.254.254.1:2376"],
  "tlsverify": true,
  "tlscacert": "/etc/docker/certs/ca.pem",
  "tlscert": "/etc/docker/certs/server-cert.pem",
  "tlskey": "/etc/docker/certs/server-key.pem"
}
```

_Justification_ :

- `"hosts"` : Définit que Docker écoutera à la fois sur le socket Unix local (pour l'accès CLI direct) et sur le port TCP sécurisé 2376 de l'interface factice `10.254.254.1`.
- `"tlsverify": true` : Applique le TLS mutuel, ce qui signifie que le serveur et le client doivent présenter et vérifier des certificats valides.
- `"tlscacert"`, `"tlscert"`, `"tlskey"` : Spécifient les chemins d'accès au certificat de l'autorité de certification, au certificat du serveur et à la clé privée du serveur, respectivement.

### Étape 4.2 : Redémarrer le Démon Docker

Redémarrez Docker pour charger les paramètres API et TLS mis à jour.

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

_Justification_ : Cela recharge les configurations systemd et redémarre Docker, appliquant les nouveaux paramètres de `daemon.json`.

### Étape 4.3 : Vérifier la Connexion TLS Sécurisée à Distance

Testez la connexion mTLS depuis votre hôte à l'aide de l'interface de ligne de commande Docker et des certificats clients.

#### Étape 4.3.1 : Définir les Variables d'Environnement Docker

Configurez l'environnement de votre shell pour pointer vers vos certificats clients et le point d'accès API Docker sécurisé.

```bash
export DOCKER_TLS_VERIFY="1"
export DOCKER_CERT_PATH="/opt/docker_conf_m8/certs"
export DOCKER_HOST="tcp://10.254.254.1:2376"
```

_Justification_ : Ces variables indiquent à la CLI Docker de se connecter via TLS, de vérifier les certificats et de localiser vos identifiants clients.

#### Étape 4.3.2 : Exécuter une Commande de Test

Tentez une commande Docker de base pour confirmer la connectivité.

```bash
docker ps
```

_Résultat attendu_ : Une liste de conteneurs en cours d'exécution (éventuellement vide) sans aucune erreur de négociation TLS.
_Justification_ : Une exécution réussie confirme que votre CLI Docker peut communiquer en toute sécurité avec le démon Docker via le point d'accès TCP sécurisé par mTLS.

## Phase 5 : Durcissement de l'Accès Réseau avec UFW

Configurez UFW pour créer un environnement très restreint pour votre API Docker.

**AVERTISSEMENT DE SÉCURITÉ CRITIQUE** : Lors de l'activation d'UFW, il est absolument essentiel d'autoriser le trafic SSH _avant_ d'activer le pare-feu, sinon vous risquez de perdre la connectivité à distance à votre serveur !

### Étape 5.1 : Autoriser l'Accès SSH (Prérequis Crucial)

Permettez les connexions SSH entrantes pour éviter le verrouillage.

```bash
sudo ufw allow ssh comment 'Autoriser l'accès SSH'
# Si votre serveur SSH fonctionne sur un port non standard (par exemple, 2222), utilisez :
# sudo ufw allow 2222/tcp comment 'Autoriser SSH sur un port personnalisé'
```

_Justification_ : Cette règle autorise explicitement les connexions SSH entrantes, vous empêchant d'être bloqué lorsque le pare-feu est activé.

### Étape 5.2 : Définir les Politiques de Pare-feu par Défaut

Définissez les comportements par défaut d'UFW pour le trafic entrant et sortant, puis activez le pare-feu.

_Justification_ : `ufw default deny incoming` fournit une politique de sécurité de base forte, bloquant toutes les connexions entrantes non sollicitées. `ufw default allow outgoing` facilite les opérations réseau sortantes normales. ### Étape 5.3 : Autoriser l'Accès à l'API Docker depuis le Réseau de Traefik

Étant donné que Traefik s'exécute dans un réseau bridge Docker (`traefik_proxy`) et non directement sur la pile réseau de l'hôte, son trafic vers l'interface factice `docker0` proviendra du sous-réseau de ce réseau bridge. Vous devez explicitement autoriser ce trafic.

_Justification_ : Cette règle est cruciale pour permettre une communication sécurisée.
